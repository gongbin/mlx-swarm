How it works

        
mlx-swarm turns a few Apple Silicon Macs into one inference service. There are three roles:

        

          
Coordinatorone per cluster: OpenAI-compatible API, routing, failover, batch queue, this dashboard

          
Agentone per Mac: finds the coordinator over Bonjour, supervises the worker, reports health, runs batch tasks

          
Workeran MLX server holding one model, inside the Mac's memory budget

        

        
Macs serve models in two ways, and you can mix them:

        
    
          
  • Replicas: each Mac holds the whole model. Requests go to the least-loaded Mac; a conversation stays on the Mac that has its prompt cache. Best for throughput.
    • 
          
  • Pipeline groups: a model too large for one Mac is split by layers across several Macs (Thunderbolt or Ethernet). The group appears as one node.
    • 
        


        
Install

        
Requirements: Apple Silicon Macs running macOS 14 or later, with all of them on the same network. A Thunderbolt cable between Macs is the fastest link for pipeline groups. Run on every Mac:


curl -LsSf https://astral.sh/uv/install.sh | sh          # Python package manager
git clone https://github.com/gongbin/mlx-swarm.git ~/mlx-swarm
cd ~/mlx-swarm && uv sync

        
Keep the project outside ~/Documents, ~/Desktop and ~/Downloads. macOS blocks background services from those folders unless you grant extra permissions.


        
Get a model

        
Any model that mlx-lm can load works. Ready-made quantized models are on Hugging Face under mlx-community. Put them under models/:


# from Hugging Face
uvx --from huggingface_hub hf download mlx-community/Qwen3-8B-4bit --local-dir models/Qwen3-8B-4bit

# from the ModelScope mirror (faster in mainland China)
sh bench/fetch_model.sh Qwen3-8B-4bit

# or quantize an original model yourself
uv run mlx_lm.convert --hf-path Qwen/Qwen3-8B -q --q-bits 4 --mlx-path models/Qwen3-8B-4bit

        
Each Mac needs its own copy at the same relative path. Copy it from a Mac that already has it:


rsync -a --progress models/Qwen3-8B-4bit/ other-mac.local:mlx-swarm/models/Qwen3-8B-4bit/

        
How large a model fits?

        
A worker uses at most about 60% of the GPU's working set by default (--mem-budget-gb changes it), so the Mac stays usable. As a rule of thumb, the weights' size on disk plus 2 GB for the KV cache must fit that budget. A 16 GB Mac holds an 8B 4-bit model (4.6 GB) comfortably; larger models go to a bigger Mac or a pipeline group. Before every load the worker checks free memory and disk (20 GB minimum by default), and it refuses to start rather than make macOS swap.


        
Start the coordinator

        
Pick one Mac, usually the one that is always on. Install the coordinator there as a login service, which restarts after crashes and reboots:


uv run swarm service install coordinator
uv run swarm ui        # opens this dashboard

        
It listens on port 8000 and announces itself over Bonjour, so agents on the network find it without configuration. To manage the cluster from other machines, give it an admin token (see Security):


uv run swarm service install coordinator --admin-token "$(openssl rand -hex 16)"


        
Add a Mac to the cluster

        
    
          
  1. Install mlx-swarm and copy the model to the new Mac.
    2. 
          
  2. Optional: measure its memory bandwidth, which the router uses as the Mac's speed: uv run python bench/probe.py.
    3. 
          
  3. Install the agent as a login service:

    uv run swarm service install agent --model models/Qwen3-8B-4bit --job-slots 4
    4. 
          
  4. When macOS asks to allow the app to find devices on the local network, allow it. Without this permission the agent cannot reach the coordinator.
    5. 
          
  5. Within a few seconds the Mac appears on the Overview page (or run uv run swarm nodes).
    6. 
        

        
Useful agent options (other options are passed through to the MLX server):

        

          
OptionMeaning

          
--model DIRmodel to serve; clients call it by the directory name (change with --served-name)

          
--job-slots Nbatch tasks this Mac runs at once (default 2, 0 for none)

          
--decode-concurrency Ninteractive requests batched together by the worker

          
--mem-budget-gb Gmemory cap for the worker

          
--draft-model DIRenable speculative decoding

          
--hostfile FILErun a pipeline group instead of a single Mac

          
--coordinator URLskip Bonjour discovery, e.g. http://10.0.0.5:8000

          
--allow-sleeplet the Mac sleep while serving (it is kept awake by default)

        

        
To serve another model on the same Mac, run service install agent again with the new --model. The new install replaces the old one. To take the Mac out of the cluster, run uv run swarm service uninstall agent.


        
Split a model too large for one Mac

        
You do not slice files by hand. Every Mac in the group keeps the full model directory at the same path, and each one loads only its own layers. The planner picks how many layers go where, from each Mac's memory budget and bandwidth.

        
1. Describe the group in a hostfile

        
The first entry is the Mac that starts the group. ips is the address the Macs use to talk to each other; a Thunderbolt link-local address is best.


[
  {"name": "studio", "ssh": "127.0.0.1",       "ips": ["169.254.10.1"], "mem_budget_gb": 20,  "bandwidth_gbs": 122},
  {"name": "mini",   "ssh": "me@mini.local",   "ips": ["169.254.10.2"], "mem_budget_gb": 8.5, "bandwidth_gbs": 101}
]

        
2. Check the plan (nothing is loaded)


uv run swarm plan --model models/Qwen3-30B-A3B-6bit --hostfile hosts.json

        
It prints the layers and memory per Mac, the expected tok/s, and whether a single Mac would be faster. --mode throughput leaves more room for concurrent requests.

        
3. Start the group


uv run swarm service install agent --model models/Qwen3-30B-A3B-6bit --hostfile hosts.json --job-slots 0

        
The first Mac must be able to ssh into the others without a password, and every Mac needs the same project path and the same uv.lock. Only the first Mac runs an agent for the group. If any member fails, the whole group restarts.


        
Speculative decoding

        
A small draft model from the same family guesses a few tokens ahead and the large model checks them in one pass. The output is unchanged, and a single stream gets about 2× faster. mlx-swarm uses it only while a request runs alone. When other requests arrive, the running request is handed to normal batching mid-stream, so throughput under load does not drop.


sh bench/fetch_model.sh Qwen3-0.6B-4bit
uv run swarm service install agent --model models/Qwen3-8B-4bit --draft-model models/Qwen3-0.6B-4bit --num-draft-tokens 3


        
Use the API

        
Point any OpenAI SDK at http://<coordinator>:8000/v1. See the API page for your address, keys and code samples.

        
    
          
  • Model name: the directory name, e.g. Qwen3-8B-4bit. GET /v1/models lists what is being served.
    • 
          
  • Conversations: send the same X-Session-Id header (or OpenAI user field) for every turn. The conversation then stays on one Mac and reuses its prompt cache.
    • 
          
  • Qwen3 thinking: pass "chat_template_kwargs": {"enable_thinking": false} to turn it off.
    • 
          
  • Batch jobs: uv run swarm jobs submit tasks.jsonl --model Qwen3-8B-4bit --wait -o results.jsonl, or use the Batch jobs page. Each line is {"custom_id": "...", "body": {...}} (OpenAI Batch format) or simply {"prompt": "..."}.
    • 
          
  • CLI: swarm chat "Hello", swarm nodes, swarm jobs list. With API keys enabled, set SWARM_API_KEY.
    • 
        


        
Operate the cluster

        
    
          
  • Drain a node on the Overview page before maintenance. It finishes its running requests but gets no new ones. Resume brings it back.
    • 
          
  • Remove forgets a Mac that is gone for good. A live agent registers again on its next heartbeat.
    • 
          
  • Services: uv run swarm service status, uv run swarm service logs agent -n 100 (logs live in ~/Library/Logs/mlx-swarm/).
    • 
          
  • Upgrade: git pull && uv sync on every Mac, then run the same service install command again to restart with the new code. Batch jobs survive coordinator restarts.
    • 
          
  • Failures: a crashed worker is restarted by its agent, and a crashed agent by launchd. Requests move to other Macs, and leased batch tasks return to the queue after 30 s.
    • 
        


        
Security

        
    
          
  • The API is open until you create the first key on the API page. From then on every /v1 request needs Authorization: Bearer sk-swarm-…. Keys are stored hashed and shown once.
    • 
          
  • Managing the cluster (nodes, keys) is allowed from the coordinator's own Mac, or with the coordinator's --admin-token, which you enter with the Token button.
    • 
          
  • Agents talk to the coordinator without authentication, so run the cluster on a network you trust. To expose the API to the internet, put it behind a reverse proxy with TLS, and enable API keys.
    • 
        


        
Troubleshooting

        

          
SymptomFix

          
A Mac never shows upRun uv run swarm discover on it. If nothing is found, allow Local Network for the Python app in System Settings › Privacy & Security, or pass --coordinator http://IP:8000.

          
Agent log stays empty after installThe project is in a protected folder. Move it to ~/mlx-swarm, or give Full Disk Access to uv's Python.

          
refusing to run in the logThe resource guard stopped a load that would not fit. Free disk space (20 GB minimum), close memory-hungry apps, or use a smaller model or a pipeline group.

          
A node is marked offlineNo heartbeat for 15 s, or less than 10% memory free. Check swarm service logs agent on that Mac.

          
Pipeline group does not startCheck passwordless ssh from the first Mac, the same project path and uv.lock on each Mac, and that the ips in the hostfile are reachable.

        

      


      
      

        
工作原理

        
mlx-swarm 把几台 Apple Silicon Mac 组成一个推理服务，其中有三种角色：

        

          
Coordinator每个集群一个：OpenAI 兼容 API、路由、故障切换、批量队列、本控制台

          
Agent每台 Mac 一个：通过 Bonjour 找到 Coordinator，守护 Worker，上报健康状态，执行批量任务

          
Worker加载一个模型的 MLX 服务，内存用量限制在本机预算以内

        

        
Mac 有两种部署方式，可以混用：

        
    
          
  • 副本：每台 Mac 都加载完整模型。请求发给最空闲的 Mac，同一个对话留在持有其 prompt cache 的机器上。适合追求吞吐量。
    • 
          
  • 流水线组：单台装不下的模型按层切分到多台 Mac 上（通过雷雳线或以太网），整个组作为一个节点对外服务。
    • 
        


        
安装

        
要求：运行 macOS 14 或更高版本的 Apple Silicon Mac，所有机器在同一网络。流水线组最好用雷雳线把 Mac 直连。在每台 Mac 上运行：


curl -LsSf https://astral.sh/uv/install.sh | sh          # Python 包管理器
git clone https://github.com/gongbin/mlx-swarm.git ~/mlx-swarm
cd ~/mlx-swarm && uv sync

        
不要把项目放在 ~/Documents、~/Desktop 或 ~/Downloads 下。macOS 默认不允许后台服务访问这些文件夹，需要额外授权。


        
获取模型

        
只要 mlx-lm 能加载的模型都可以使用。Hugging Face 上的 mlx-community 提供现成的量化模型。模型放在 models/ 下：


# 从 Hugging Face 下载
uvx --from huggingface_hub hf download mlx-community/Qwen3-8B-4bit --local-dir models/Qwen3-8B-4bit

# 从 ModelScope 镜像下载（国内更快）
sh bench/fetch_model.sh Qwen3-8B-4bit

# 或者自己量化原始模型
uv run mlx_lm.convert --hf-path Qwen/Qwen3-8B -q --q-bits 4 --mlx-path models/Qwen3-8B-4bit

        
每台 Mac 都需要在相同的相对路径下有一份模型。可以从已有模型的 Mac 上复制：


rsync -a --progress models/Qwen3-8B-4bit/ other-mac.local:mlx-swarm/models/Qwen3-8B-4bit/

        
多大的模型能装下？

        
为了不影响 Mac 的日常使用，Worker 默认最多使用 GPU 工作集的约 60%（可以用 --mem-budget-gb 调整）。粗略估算：模型文件大小加上 2 GB KV cache 不能超过这个预算。16 GB 的 Mac 可以轻松运行 8B 4-bit 模型（4.6 GB）。更大的模型请放到内存更大的 Mac 上，或者使用流水线组。每次加载前 Worker 都会检查空闲内存和磁盘空间（默认至少 20 GB），如果放不下就拒绝启动，而不是让 macOS 开始换页。


        
启动 Coordinator

        
选一台 Mac，通常是一直开着的那台。把 Coordinator 安装为登录服务，崩溃或重启后会自动恢复：


uv run swarm service install coordinator
uv run swarm ui        # 打开本控制台

        
它监听 8000 端口，并通过 Bonjour 广播自己，网络中的 Agent 无需配置就能找到它。如果想在其他机器上管理集群，请给它设置管理员令牌（见安全）：


uv run swarm service install coordinator --admin-token "$(openssl rand -hex 16)"


        
添加一台 Mac

        
    
          
  1. 在新 Mac 上安装 mlx-swarm，并复制模型。
    2. 
          
  2. 可选：测量本机内存带宽（路由器把它作为这台 Mac 的速度）：uv run python bench/probe.py。
    3. 
          
  3. 把 Agent 安装为登录服务：

    uv run swarm service install agent --model models/Qwen3-8B-4bit --job-slots 4
    4. 
          
  4. macOS 询问是否允许查找本地网络上的设备时，点「允许」。没有这项权限，Agent 无法连接 Coordinator。
    5. 
          
  5. 几秒钟后，这台 Mac 会出现在总览页面（也可以运行 uv run swarm nodes）。
    6. 
        

        
常用的 Agent 参数（其他参数会原样传给 MLX 服务）：

        

          
参数含义

          
--model DIR要部署的模型；客户端用目录名调用（可以用 --served-name 修改）

          
--job-slots N这台 Mac 同时执行的批量任务数（默认 2，0 表示不接批量任务）

          
--decode-concurrency NWorker 合并成一批处理的交互请求数

          
--mem-budget-gb GWorker 的内存上限

          
--draft-model DIR启用投机解码

          
--hostfile FILE运行流水线组，而不是单台 Mac

          
--coordinator URL跳过 Bonjour 自动发现，例如 http://10.0.0.5:8000

          
--allow-sleep服务期间允许 Mac 休眠（默认保持唤醒）

        

        
要在同一台 Mac 上换一个模型，用新的 --model 再运行一次 service install agent，新安装会替换旧的。要让这台 Mac 退出集群，运行 uv run swarm service uninstall agent。


        
切分单机装不下的模型

        
不需要手动切分文件。组内每台 Mac 都在相同路径下保存完整的模型目录，各自只加载自己负责的层。每台 Mac 分多少层，由规划器根据各自的内存预算和带宽决定。

        
1. 用 hostfile 描述这个组

        
第一项是启动这个组的 Mac。ips 是 Mac 之间互相通信的地址，最好使用雷雳线的链路本地地址。


[
  {"name": "studio", "ssh": "127.0.0.1",       "ips": ["169.254.10.1"], "mem_budget_gb": 20,  "bandwidth_gbs": 122},
  {"name": "mini",   "ssh": "me@mini.local",   "ips": ["169.254.10.2"], "mem_budget_gb": 8.5, "bandwidth_gbs": 101}
]

        
2. 查看规划（不会加载模型）


uv run swarm plan --model models/Qwen3-30B-A3B-6bit --hostfile hosts.json

        
输出每台 Mac 分到的层数和内存、预计 tok/s，以及单机运行是否会更快。--mode throughput 会为并发请求留出更多内存。

        
3. 启动这个组


uv run swarm service install agent --model models/Qwen3-30B-A3B-6bit --hostfile hosts.json --job-slots 0

        
第一台 Mac 需要能免密 ssh 登录其他机器，每台 Mac 的项目路径和 uv.lock 都要相同。整个组只在第一台 Mac 上运行一个 Agent。任何一台成员故障时，整个组会一起重启。


        
投机解码

        
用同系列的小草稿模型先猜几个 token，再由大模型一次性验证。输出不变，单路速度约提高 2 倍。mlx-swarm 只在一个请求单独运行时使用投机解码。一有其他请求进来，正在生成的请求会在中途转入普通批处理，因此高负载下的吞吐量不会下降。


sh bench/fetch_model.sh Qwen3-0.6B-4bit
uv run swarm service install agent --model models/Qwen3-8B-4bit --draft-model models/Qwen3-0.6B-4bit --num-draft-tokens 3


        
调用 API

        
把任意 OpenAI SDK 指向 http://<coordinator>:8000/v1 即可。你的地址、Key 和示例代码见 API 页面。

        
    
          
  • 模型名：模型的目录名，例如 Qwen3-8B-4bit。GET /v1/models 列出当前部署的模型。
    • 
          
  • 多轮对话：每一轮都带上相同的 X-Session-Id 请求头（或 OpenAI 的 user 字段），对话就会留在同一台 Mac 上，复用其 prompt cache。
    • 
          
  • Qwen3 思考模式：传入 "chat_template_kwargs": {"enable_thinking": false} 即可关闭。
    • 
          
  • 批量任务：uv run swarm jobs submit tasks.jsonl --model Qwen3-8B-4bit --wait -o results.jsonl，或者使用批量任务页面。每行是 {"custom_id": "...", "body": {...}}（OpenAI Batch 格式），或者直接写 {"prompt": "..."}。
    • 
          
  • 命令行：swarm chat "你好"、swarm nodes、swarm jobs list。启用 API Key 后，需要设置 SWARM_API_KEY。
    • 
        


        
日常运维

        
    
          
  • 维护前，在总览页面排空节点：它会处理完正在运行的请求，但不再接收新请求。点击恢复重新上线。
    • 
          
  • 移除：从集群中删除一台已经不再使用的 Mac。如果它的 Agent 仍在运行，下次心跳时会重新注册。
    • 
          
  • 服务：uv run swarm service status、uv run swarm service logs agent -n 100（日志在 ~/Library/Logs/mlx-swarm/）。
    • 
          
  • 升级：在每台 Mac 上运行 git pull && uv sync，再运行一次原来的 service install 命令，以新代码重启。Coordinator 重启不会丢失批量任务。
    • 
          
  • 故障：Worker 崩溃后由 Agent 重启，Agent 崩溃后由 launchd 拉起。请求会转到其他 Mac 上，已领取的批量任务在 30 秒后回到队列。
    • 
        


        
安全

        
    
          
  • 在 API 页面创建第一个 Key 之前，API 是开放的。之后，所有 /v1 请求都需要 Authorization: Bearer sk-swarm-…。Key 以哈希形式保存，只在创建时显示一次。
    • 
          
  • 管理集群（节点、Key）只能在 Coordinator 所在的 Mac 上进行，或者使用 Coordinator 的 --admin-token（点击令牌按钮输入）。
    • 
          
  • Agent 与 Coordinator 之间的通信目前没有鉴权，请在可信的网络中运行集群。如果要把 API 开放到公网，请放在支持 TLS 的反向代理后面，并启用 API Key。
    • 
        


        
常见问题

        

          
现象解决方法

          
某台 Mac 一直没有出现在那台 Mac 上运行 uv run swarm discover。如果找不到 Coordinator，在「系统设置 › 隐私与安全性 › 本地网络」里允许对应的 Python 程序，或者加上 --coordinator http://IP:8000。

          
安装服务后 Agent 日志一直为空项目在受保护的文件夹中。把项目移到 ~/mlx-swarm，或者给 uv 的 Python 授予「完全磁盘访问权限」。

          
日志中出现 refusing to run资源保护阻止了一次放不下的加载。请清理磁盘（至少 20 GB）、关闭占用内存多的程序，或者换用更小的模型、流水线组。

          
节点显示离线15 秒没有心跳，或者空闲内存低于 10%。在那台 Mac 上查看 swarm service logs agent。

          
流水线组无法启动检查第一台 Mac 能否免密 ssh 登录其他机器，各台 Mac 的项目路径和 uv.lock 是否相同，hostfile 中的 ips 是否可达。
